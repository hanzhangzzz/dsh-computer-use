# 桌面控制实施方案与任务拆分

日期：2026-08-26。状态：待人类裁决。上级文档：docs/master-plan.md、docs/desktop-control-plan.md。

目标（人类给定，本文一切服从它）：**获得所有 mac app 的操作能力，不打扰用户，agent 有独立的
光标和事件体系。**

## 一、当前站位（全部实测，可复跑）

| 能力 | 状态 | 证据 |
|---|---|---|
| 读后台应用的结构 | ✅ 已实现 | 计算器 24 元素 / VS Code 845 / 微信开发者工具 13（需 AXManualAccessibility） |
| 按索引操作，带身份校验 | ✅ 已实现 | 验收 press-by-index：显示 `5` → `7×6 \| 42` |
| 坐标命中测试后操作 | ✅ 已实现 | `AXUIElementCopyElementAtPosition`，命中不符则拒绝且不按下 |
| 读应用显示的内容 | ✅ 刚补齐 | 验收发现的盲区，helper 现返回窗口可读文本 |
| 窗口移动/缩放 | ✅ 已实现 | (510,421)→(630,481)→还原，光标焦点未动 |
| 不打扰不变量 | ✅ 每个动作运行时自检 | 9/9 验收用例全部 `focusStolen=false cursorMoved=false` |
| **自由拖拽** | ❌ **未通** | AX 无拖拽动作；合成鼠标事件三条公开通道全部失败 |
| **独立可见光标** | ❌ 未做 | — |
| 按窗口截图 | ❌ 未做 | `CGWindowListCreateImage` 已废弃，须走 ScreenCaptureKit |

一句话：**除自由拖拽外，目标的其余部分已经用零私有 API 达成——但只在 AX 树可用的应用上。**

### 覆盖率（第一轮对抗审视实测，2026-08-26）

对本机 22 个运行中应用逐个快照：4 个无窗口（Terminal 等，属正确行为不计），**其余 18 个里
11 个元素数 ≥20 可实际操作（61%）**。分布：VS Code 136、闲管家 95、千牛 65、Kimi 62、
Clash Verge 55、Chrome 42、备忘录 39、访达 35、预览 24、飞书 20、微信开发者工具 13。

**真正够不到的**：微信（3 个无名元素）、Codex app（3 个无名）、网易 UU（11 个全无名）。
这三个都拒绝 `AXManualAccessibility`（返回 -25205 属性不支持），属于自绘 UI，只能靠第 3 层。

这个数字修正了本方案初稿的一处断言。初稿声称前两层已覆盖目标，但没有任何覆盖率数据支撑——
而第一次测出来的数字（22 个应用里仅 8 个可用）是错的，见下。

## 二、必做的探索实验（E 系列）

已跑完的在前，未跑的给出设计和判据。判据必须是**可机器判定的**，不接受"看起来работа"。

| # | 问题 | 状态 | 判据 |
|---|---|---|---|
| E1 | 公开 API 能否把鼠标事件送进后台窗口 | ✅ 已跑，**否** | 键盘 `postToPid` 生效；鼠标三通道全败；全局 `CGEventPost` 打给最上层窗口（曾误判为"被忽略"，已更正） |
| E2 | SkyLight 私有通道能否补上 | ✅ 已跑，**当前实现不通** | 12 种组合（3 焦点策略 × 4 坐标姿态）全部未送达，两条假设被证伪 |
| E3 | 参照实现用了什么 | ✅ 已跑 | DoubaoWork 的 `libaha_cua.dylib` 未 strip，701 条 API 已存档 |
| **E4** | **`prevent_activation` 写的是哪个 AX 属性** | **待跑** | 对候选属性（`AXEnhancedUserInterface` 等）逐个 read/write，观察目标应用激活行为是否被抑制。判据：设置后用 `open -a` 拉起目标，`isActive` 仍为 false |
| **E5** | **focus-acquire 需要哪几个事件** | **待跑** | 参照实现构造的是 `vector<CGEvent>`，且入参含 `windowRect`。判据：某个组合下计算器显示改变 |
| **E6** | **`stamp_mouse_event` 需要设哪些整数字段** | **待跑** | `set_synthetic_focus_integer_field(event, field, value)` 按编号设字段。判据：枚举 CGEventField 编号做二分，找到使事件被接受的最小字段集 |
| **E7** | ScreenCaptureKit 按窗口截图 | 待跑 | 判据：被完全遮挡的窗口仍截到正确内容，且尺寸等于窗口 CSS 像素 |
| **E8** | 独立光标 overlay | 待跑 | 判据：`NSWindow` 覆盖层显示 agent 光标，`canBecomeKeyWindow=false`，不接收点击，不影响命中测试 |
| **E9** | 签名 helper 是否改变权限行为 | 待跑 | 判据：独立签名 + 自有辅助功能授权后重跑 E1/E2，结果是否变化 |

E4–E6 是**串行依赖**的：不解决 E4/E5，E6 无从判断失败是字段问题还是焦点问题。这三个跑通与否，
决定后面是走 A 路线还是 B 路线。

## 三、验收 case（已建成并全绿）

`experiments/desktop-acceptance/run.py`，9 个能力用例，`9/9 passed`。

设计上刻意区别于浏览器那套验收，因为那套被自己的判据坑过两次（7/15 任务的判据词写在题面里；
`httpbin-elements` 靠匹配编号列表里的 "1" 通过而模型答案是 0）。两条硬规则：

1. **判据必须观察到被控应用发生变化**，读它自己的状态，不读模型的话，也不读不会变的量
   （第一版拿窗口标题做判据，而标题按了按钮也不变，用例恒绿——已修）。
2. **不打扰不变量逐动作校验**，任一动作报 `focusStolen` 或 `cursorMoved` 为真，整个用例判失败。

覆盖：枚举 / 索引按压 / 身份失配拒绝 / 坐标命中 / 坐标失配拒绝 / 未变折叠 / 窗口几何 /
越界索引 / 应用未运行。

**尚未覆盖、须补的**：拖拽（等 E5/E6）、截图（等 E7）、独立光标（等 E8）、多应用切换、
Electron 目标（微信开发者工具，已有手工验证但未进套件）、断连与应用退出中途。

模型级验收是另一套，按仓库无人值守纪律须人在场，不在本套件内。

## 四、方案：三层降级，私有 API 只在最后一层

```
第 1 层  结构操作（AX 动作）        零私有 API，后台，最准     ← 已实现，主路径
第 2 层  坐标命中后操作（AX 命中）  零私有 API，后台，可预检   ← 已实现
第 3 层  合成指针（SkyLight）      私有 API，后台，覆盖全部   ← 待攻克，仅拖拽/画布用
```

前两层已覆盖"所有 mac app"里能被 AX 表达的部分，且完全满足"不打扰"。第 3 层只服务于
AX 表达不了的交互——自由拖拽、画布内绘制、AX 覆盖差的自绘应用。

**分层的意义是失效隔离**：第 3 层依赖私有符号，macOS 大版本升级可能失效（yabai 记录显示
Sequoia 15.3 就有私有 API 返回垃圾值）。它必须能独立探测、独立降级，失效时前两层照常工作并
明确告知模型"拖拽当前不可用"，而不是整条桌面路径一起挂掉。

### 路线分叉

- **A 路线（E4–E6 跑通）**：实现第 3 层，目标完整达成。
- **B 路线（E4–E6 不通）**：第 3 层降级为"独占模式"——显式征得用户同意后，短暂提升目标窗口
  并用公开 `CGEventPost` 完成拖拽，完成后还原。能力完整但那几秒钟打扰用户。这是诚实的退路，
  不是失败。

两条路线的**前两层完全相同**，所以 E4–E6 的成败不阻塞任何其它任务。

## 五、任务拆分

依赖关系写在括号里。无依赖的可并行。

**T1 独立光标 overlay**（无依赖）
借 `NSWindow` 覆盖层画 agent 光标，`canBecomeKeyWindow=false`、`ignoresMouseEvents=true`，
不参与命中测试。动作前把光标动画移到目标位置，按下时播放反馈。
验收：新增用例断言 overlay 存在、不吃点击、且用户真实光标未受影响。

**T2 ScreenCaptureKit 按窗口截图**（无依赖）
`CGWindowListCreateImage` 已废弃，须换 SCK。硬性规定按窗口截，绝不整屏——640k 像素预算下
4K 整屏会把 20px 按钮压到 5.6px。
验收：遮挡状态下截到正确内容；返回尺寸等于窗口逻辑像素。

**T3 Node provider 补齐动作面**（无依赖）
把 helper 已有但 provider 未暴露的能力接上：`action`（任意具名动作）、`window`（几何）、
`text`（可读内容）。`pressKey` 与 `screenshot` 目前抛"未实现"，需按 T2 落地。
验收：现有 vitest 套件扩展，全绿。

**T4 挂进发布入口**（依赖 T3）
`dsh-tool-computer` 的 `apply` 组装 macOS provider，白名单配置透出，helper 二进制随包分发。
验收：`pnpm run typecheck && test && build` 全绿；`pnpm -r pack --dry-run` 内含 helper。

**T5 验收套件扩容**（依赖 T1/T2/T3）
补：Electron 目标（微信开发者工具）、多 surface 切换、截图、光标、应用中途退出。
验收：套件通过率与失败原因均入 results/。

**T6 E4–E6 攻坚**（无依赖，但决定 T7）
按第二节的判据逐个跑。**时间盒：三个实验各一轮，不通就转 B 路线**，不做无限期逆向。

**T7 第三层落地**（依赖 T6）
A 路线实现 SkyLight 注入 + 拖拽；B 路线实现独占模式 + 用户确认。
验收：拖拽用例——在目标应用内把一个元素拖到另一位置，读回状态确认，且 A 路线下不变量保持。

**T8 模型级验收**（依赖 T4/T5，须人在场）
仿 `phase2-acceptance/run.py`，判据同样只认应用状态。log 级核验为汇报前置。

## 六、明确不做

- 不整屏截图（像素预算实测否决）。
- 不移植参照实现的代码。读它的 API 图谱定位机制可以，抄实现不行——许可与来源都得干净。
- 不在无人值守下跑桌面模型任务（2026-08-25 安全事件产物）。
- 第 3 层不通就不硬上，转 B 路线；不为它无限期投入。

## 七、什么数据会推翻本方案

- E4–E6 全通但拖拽在真实应用上仍不可用 → 说明机制理解错了，第 3 层整体重估。
- 前两层在真实任务里的覆盖率远低于预期（大量应用 AX 树空） → 分层假设失效，
  第 3 层从"补充"升级为"主路径"，优先级完全反转。
- 独立光标 overlay 影响命中测试或被应用感知 → T1 方案作废，需另寻显示途径。
